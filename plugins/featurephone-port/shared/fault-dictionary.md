# Fault dictionary

The plugin's index of pain. Every failure the reference port hit, merged across all phases, keyed
by the text a user would actually search for.

**How to use it.** If you have a literal message, start at [§1](#1-verbatim-messages). If you have a
behaviour ("it stutters", "it works on my desk only"), go to the matching section in
[§2](#2-behavioural-symptoms). Each row names the skill that owns the fix — invoke that skill and
it will route you to the reference file with the mechanism and the repair.

Owning skills: `archive-prep` · `emulator-core` · `guest-re` · `android-host` · `save-integrity` ·
`server-revival` · `port-shipping` · `port-triage`.

Messages are quoted the way the reference implementation emits them. Your fork's wording may differ;
match on the distinctive fragment, not the whole line.

## 1. Verbatim messages

| message | what it actually means | skill |
|---|---|---|
| `AllocationFailure` after 20–40 minutes of play, with plenty of free heap | The guest heap's list allocator never coalesces adjacent free blocks, so the block count rises monotonically and the largest contiguous free block shrinks toward zero. The progressive slowdown before it is the same cause — every free-list walk gets longer. Fix: coalesce lazily **in the walk**, not in `free` (the chain is singly linked forward, so `free` cannot reach its predecessor). **Discriminator:** this one needs tens of minutes and the requested size is sane. A failure seconds after the title screen, with a *negative* size, is the next row and a completely different fault. | `emulator-core` |
| `AllocationFailure` with a **negative** size in the argument register (e.g. `R0: 0xffffffe4`), seconds after the title screen — or a fatal error from an event-queue call unrelated to anything you changed | Not the allocator. A generated or patched data member in the archive is **present but stale**, so it disagrees with a guest constant about that table's row count; the guest's parser walks past the end of the array and reads a length field back as a negative number. An **asset** fault wearing an emulator fault's clothes: the build script, the signature check and a launch-and-look smoke test all pass, because the death is *after* the title. Ten consecutive releases shipped that way in the reference port. | `archive-prep` / `port-shipping` |
| `"App not installed"` / the update is refused on a phone that already has the app | Either `versionCode` is not strictly greater than the installed one, or the signing certificate changed. The second is unrecoverable without an uninstall, which deletes the player's saves **and the save vault with them** — so never offer an uninstall as a workaround for anything. | `port-shipping` / `save-integrity` |
| Output is `app-release-unsigned.apk` instead of `app-release.apk` | No complete signing configuration resolved, so the build succeeded and produced something nobody else can install. The filename *is* the diagnostic — treat any `*unsigned*` output as a build failure. | `port-shipping` |
| `called 'Option::unwrap()' on a 'None' value` in the JVM value layer, during boot | `loadClass` returned null: the descriptor's main-class name is wrong, misspelled, or not a class the guest's own class resolver knows. | `archive-prep` |
| `called 'Result::unwrap()' on an 'Err' value: NotFound` in the Java `io/file` layer, **printed after `loaded`** | The loader tried to open `<AID>.jar` and it is not in the virtual filesystem. Two causes, both in the archive: the descriptor has CR bytes (`AID:XXXX\r` composes `XXXX\r.jar`), or the AID simply does not match the jar's basename. | `archive-prep` |
| `Installed 1 hooks` in the boot log, and the generic compiler-pattern hooks never fire on any build | The patch installer returns after the first matching entry class, so a title that has a hash-keyed entry never receives the hash-less generic entries. The count line *looks* like a success line and is the only symptom. Install every matching class as one unit: resolve all hooks first, validate patch-versus-hook overlap on the merged list, let the keyed entry win a conflict, and register the dispatcher exactly once. | `emulator-core` |
| `Invalid bss_size in filename client.bin: cannot parse integer from empty string` | Somebody renamed the native member and stripped its numeric suffix. That suffix is the BSS size; it exists nowhere else. | `archive-prep` |
| `client.bin* not found in jar` | No jar member matches the platform's native-image name prefix. Either the wrong platform was detected, or this is a bytecode title (check for `.class` files). | `archive-prep` / `port-triage` |
| `Duplicate class kotlin.jvm.internal.…` at the Gradle stage | Version skew between the game-activity artifact's Kotlin split stdlib and the one your support library pulls. Force a single stdlib version in a resolution strategy. | `port-shipping` |
| `ECONNABORTED` (`os error 103`) on every socket, seconds after the app was backgrounded | Not your server and not the network: a modern mobile OS freezes a cached process and destroys its sockets. No socket-layer rule prevents it, and raising the server's idle budget changes nothing because the reset happens within seconds. Record the transition on the way **down**, probe each live socket on the first network call after resume instead of assuming, keep an unanswered-request watchdog as the backstop — and raise the client's own screen-exit modal, because the frozen screen will not clear itself. | `android-host` / `server-revival` |
| `entry <hash>: hash matched but produced 0 patches/hooks` | The emulator's md5-keyed binary-patch table has an entry for this guest image but none of its patterns matched — the table is stale relative to the binary. Fires the moment you repack a guest binary and its md5 moves. A hash-keyed entry that yields nothing is fatal; a generic hash-less entry only warns. | `emulator-core` |
| `expected <N> records, got <N+1> — refusing` from an archive transform | Two causes, and the message names neither. Either you re-ran an in-place tool against an already-patched archive, or — for a tool that rebuilds from a pristine copy — **the pristine copy has been deleted**, so the tool is now reading its own previous output as its source. Ask whether a pristine copy still exists before you go and debug the record parser. Never delete a pristine backup: move it. | `archive-prep` |
| `failed to add native library …dll_imports.lib: file not found` | Cross-compiling from a `windows-gnu` host. rustc chooses the GNU vs LLVM `dlltool` flag set from the tool's **file name**, so a renamed `llvm-dlltool` gets a GNU-only flag it rejects, writes no import library, and the error names the missing file rather than the cause. Needs an argv-filtering shim. Does not exist on Linux, macOS or `windows-msvc`. | `port-shipping` |
| `Fatal signal 11 (SIGSEGV), code 2 (SEGV_ACCERR)` · `Cause: stack pointer is not in a rw map; likely due to stack overflow` · **two addresses alternating for the whole backtrace** · the ASCII text `"Allocation failure"` still in registers | Mutual recursion between the JVM's exception constructor and the guest allocator. Building an exception message allocates a guest `char[]`; when the guest heap is what failed, that allocation fails, and the failure is reported by constructing another exception. Fix: pre-allocate one error instance at startup while the heap is healthy, root it in a static field of a registered class, and hand it out. A plain re-entrancy guard does **not** work — it converts the SIGSEGV into a panic, because the *outer* call is the one that must not enter the exception path. | `emulator-core` |
| `Init failed with code <n>` / `wipi init failed` at boot | Wrong BSS size, or the guest asked for an init interface the emulator does not know. Check the boot log for an "unknown interface" warning first. | `emulator-core` |
| `Invalid memory access; address:0` **on the client, immediately after your server reply** | Your reply body was empty where the client's text/page builder requires non-empty content — it walks a null page list. "The minimum clean reply is an empty one" is a very attractive and very wrong inference from the disassembly. The same trap sits behind a status-only failure acknowledgement: the client's failure arm reads its message text out of that frame's body, so a refusal with no text is a crash primitive. | `server-revival` |
| `InvalidMemoryAccess(0)` / a branch to address 0 **right after a WIPI call** | The guest indexed a slot past the end of the function-pointer table you allocated, read whatever follows the allocation (zero), and branched to it. Pad the table **and** the corresponding struct; upstream slot counts are guesses, not a contract. | `emulator-core` |
| A `FatalError` the instant the game first touches a whole subsystem (network, sound, database) — no `Unimplemented` line, no null branch, nothing to trace | That carrier runtime named only a few slots of the block, and its id-to-enum conversion ends in `_ => FatalError`, which the dispatcher propagates. Any unmapped id in the block is fatal *before* a stub can log it. Range-dispatch the whole block (`base + slot`, slot in `0..N`) before the conversion, fill it from the other carrier's table by positional index — the bodies are carrier-agnostic — and give every remaining slot a logging trace stub. | `emulator-core` |
| `FatalError("Main class not found")` after a clean load | A bare jar with no descriptor. The main-class name has no other source in the archive; synthesize a descriptor. | `archive-prep` |
| `[probe] not a KTF archive` / `Unknown archive format` — clean, at load time, no panic | No recognised magic entry in the outer zip. Re-classify: this may be a different carrier, a bare jar, a `.jad`+`.jar` pair, or not a game dump at all. | `port-triage` |
| `NativeCommandError` naming compiler **warnings**, on a test or build command that actually succeeded | PowerShell 5.1 turns every native stderr line into an error record when you redirect it (`rustc … 2>&1`, `cargo … 2>&1`), so a warning marks the run failed at exit code 0 and a green selftest suite reads as a build failure. Never redirect a compiler's stderr; check the exit code, and send stderr to null if you must suppress it. | `port-shipping` |
| `… only allowed in Rust 20NN or later`, pointing into shipping source, from a standalone selftest that used to compile | The standalone test's `--edition` is pinned below the crate's, so it has been compiling the shipping source under different language rules than the real build. This is the benign direction; the malign one is a test passing under older semantics than you ship. Derive the edition from the crate, never from the command line or a CI loop. | `port-shipping` |
| `opened <create mode> and closed with NO write — record 1 deleted` (or your store's equivalent) | The guest opened a record for create and never wrote — usually because the write failed, or because your own policy guard refused it — and the deferred truncate ran at close. If the slot cursor has drifted, this deletes **another character's** record. Disarm the pending truncate on every failure and early-return path, and gate record-level deletes with the same policy as writes (a delete has no redirect: allow or refuse only). | `save-integrity` |
| `record <n> of <name> was NOT stored`, while the game showed the player a save-succeeded message | The record store's success flag was discarded, so a failed write was reported to the guest as success; the guest's own writer will propagate a failure code if you give it one. Fix the truncate disarm in the same commit, or reporting the failure honestly converts it into a delete. | `save-integrity` / `emulator-core` |
| `PANIC: … jvm.rs … called 'Option::unwrap()' on a 'None' value` on the **first host-initiated guest call** | The JVM keys per-thread state by executor task id, and the task you spawned to run the guest function has a brand-new id with no thread entry. The emulator's own callback path has always wrapped its spawns in attach/detach; the host-call path did not — which is why this feature "had never once worked on a device". Fix: an RAII attach/detach guard around every host-originated call, tolerant of the JVM not existing yet. | `emulator-core` / `guest-re` |
| `FatalError("Undefined instruction")` | A genuinely missing opcode in the interpreter. Rare — a commercial ARM feature-phone binary exercises a well-trodden subset. Add a hand-written assembly fixture with the suspect encoding. | `emulator-core` |
| `SVC handler already registered`, aborting boot, immediately after you "fixed" the hook installer | You called the single-entry installer twice instead of merging the entries into one pass. The dispatcher may be registered exactly once. | `emulator-core` |
| `Unimplemented: <id>: <name>` — exactly one line, then a frozen or black screen | A fatal WIPI-C stub. The line names the table id and the slot. Convert it to a logging no-op returning a plausible value (a "trace stub") and re-run: the game will keep walking and dump its whole API sequence for you. | `emulator-core` |
| `UnsatisfiedLinkError` at launch | The three native-library names disagree: the Cargo `[lib] name`, the `System.loadLibrary` argument, and the manifest's `android.app.lib_name`. This is a runtime error, not a build error. | `port-shipping` |
| `Unknown SVC handler category: <n>` | An SVC category the guest uses is registered by no handler. | `emulator-core` |
| `Unknown <name>` warning from the interface getter, then a fault far away later | The guest asked for an interface the loader does not know and got a null pointer back. It dies much later, at a site with no relationship to the cause. **Check this warning first on any new title.** | `emulator-core` |

## 2. Behavioural symptoms

### 2.1 Archive and first boot

| symptom | what it actually means | skill |
|---|---|---|
| The emulator prints `loaded` and then panics | `loaded` means "constructed", not "booted". Every archive fault fires afterwards, on the async boot task. On a phone this surfaces as a panic line in the log and a black screen, not as a load error. | `archive-prep` |
| A boot that worked yesterday fails after you edited the descriptor in an editor | The editor rewrote the file with CRLF line endings. The KTF and LGT descriptor parsers slice from a fixed index with no trim; the SKT parser trims, so the same edit is harmless there. Normalising CR to nothing is the entire content of the "repair" step. | `archive-prep` |
| A repack tool refuses with "changed records … != expected" | Two causes, and the count in the message points at neither. Either repacking is not idempotent and you are running it against an already-patched archive — restore the pristine copy from your backup directory — or the tool rebuilds from a pristine copy and **that copy has been deleted**, so it is now reading its own previous output as its source. Ask whether a pristine copy still exists before you go and debug the record parser. Never delete a pristine backup: move it. | `archive-prep` |
| The repacked archive is a different size from the original | Expected and harmless — a different zip implementation uses different deflate parameters and writes no extra fields. **Size is not a validity check.** Verify by re-parsing the modified member and byte-comparing every other member. | `archive-prep` |
| A fresh clone builds an APK with no game in it | The archive is gitignored (correctly), the assets directory is simply empty, and the packaging step succeeds anyway. Add a fail-fast build check for the asset's presence — the single most important hardening for a public template. | `port-shipping` |
| Boot works but saves land in an unexpected directory, or an old backup will not load | The save namespace is the descriptor's PID. Choose it once; changing it after release orphans every player's saves while leaving the app apparently healthy. The same is true of switching which carrier build you ship — the namespace and the record names both move, and the old set is invisible rather than deleted. | `archive-prep` / `save-integrity` |

### 2.2 Generated and patched assets

Anything the build consumes that is *generated* — a repacked archive, a patched data member, a
table extracted from the game's own resources — is a build input that version control does not
carry. Several rows below are that one fact wearing different clothes.

| symptom | what it actually means | skill |
|---|---|---|
| A change you committed, documented and verified is not in the built artifact, and every tool in the pipeline printed OK | The generated archive is gitignored (correctly), so it did not travel with the commit that describes it. The tables and the tools are in the repository; the bytes are on whichever machine last ran the tools, and `git log` cannot tell you which build is actually shipping. Give the generator a `--check` mode that rebuilds from the pristine original **in memory** and byte-compares the shipped artifact, exiting non-zero — and make it the first command of any session that touches assets. It answers both "are my tools current" and "has this machine's archive caught up with the repository". | `archive-prep` / `port-shipping` |
| One asset tool reports VERIFY OK, all members byte-identical, and the shipped archive still carries the old text — or a member has reverted to its pristine value | Two generators write the same archive with different strategies: one rebuilds from a pristine copy (discarding the other's work) and one edits in place (leaving the first's members pristine if it never ran). Both orders "succeed" and both print clean reports. Fix the order — rebuild-from-pristine first, in-place second, always run as a pair — and have `--check` compare only the members each tool **solely** owns, with a comment naming the co-owned member as deliberately out of scope. A check that fails spuriously gets disabled, which loses the whole gate. | `archive-prep` |
| The built package grew by roughly the size of the game archive with no content change | A tool wrote its backup or its dry-run output next to its input, inside a directory the packager takes wholesale. Route every by-product through one shared backup-path helper that lands outside anything packaged, and ignore it by **name** as well as by path. For a port the accidental extra file is licensed content, so it is a publish exposure as well as a size regression. Any procedure step of the form "then move the file by hand" is itself the defect: it has a failure rate and its failure is silent. | `archive-prep` / `port-shipping` |
| An in-game one-line description is blank for **some** records, a different subset every session, while the full detail popup for the same records is fine | Your text edit removed an in-band delimiter that the renderer scans for with no NUL test and no bound, so the scan runs off the allocation into the heap and stops at the first matching byte — a positive length (looks normal) or a negative one (draws nothing), depending on allocation history. Restore the delimiter; a bare trailing one is invisible. Establish the invariant across **all** pristine records, and assert per output row that it is present and not at index 0. A pattern holding in 100 % of the publisher's records is evidence of a renderer-enforced invariant, not of redundancy. | `archive-prep` |
| Your writer accepts a record length prefix under 256 and the guest allocates a negative size at load | The loader reads the prefix with a **signed** byte load, so the ceiling is `0x7f`, not the prefix's storage width. The bound is a property of the reader, not of the format: read the load instruction and assert that in the writer. | `archive-prep` |
| Everything after the record you edited is unreachable in-game, and your own parser stops partway through the member without erroring | A wrong record model — typically a per-record length prefix read as a file header — so the tool copied the next record's prefix through as part of the previous record's trailer, and every prefix from the edit onward is stale. Assert `consumed == filesize` in the reader **and** make the writer refuse any input that does not parse byte-exact, naming the pristine fallback in the message. | `archive-prep` |
| An override or rename table prints VERIFY OK and the shipped text is unchanged | The override key matched nothing — an index that is not in this table, or a row that moved — and a key that matches nothing is a silent no-op. Key overrides by index **and** an expected identity field, die on an identity mismatch ("refusing to rewrite a row this table did not mean"), and have verify walk every key asserting the output row starts with the new value. | `archive-prep` |
| Adding a row to a game data table crashes or draws garbage at the first screen that lists it | The row count, the allocation size and the teardown bound are hardcoded in guest code and no reader bounds-checks the index. Change them together with the data, pin the original bytes so a foreign build refuses to boot rather than walking off the table, and verify by dumping the live table in a headless run (new row present, following row all zeros). Ship them as load-time RAM patches: editing the guest image moves its hash and silently disables every performance hook keyed on it. | `guest-re` / `archive-prep` |

### 2.3 Rendering, frame pacing and game speed

| symptom | what it actually means | skill |
|---|---|---|
| **Black screen, no error, CPU busy, every dumped frame 100% black** | The host's `now()` is wall-clock and the harness ticks as fast as it can. The guest does not busy-loop — it arms a timer and yields — so no timer ever expires. Give the platform a virtual clock advanced by a fixed number of milliseconds per frame. This is the first trap every headless run hits, and the reason the millisecond flag is mandatory rather than optional. | `emulator-core` |
| Maps with a lot on screen stutter; sparse maps are fine; a full-screen effect stutters | Draw cost scales with call count × whole screen, not with pixels drawn. Every draw call reads the entire destination framebuffer out of guest memory, copies it again into a typed vector, and writes the whole thing back on drop — so a one-pixel operation pays hundreds of kilobytes of memcpy. Fix with row bands, a direct typed read, and a skip-the-read path for fills that cover their band. | `emulator-core` |
| Black horizontal bands, or stale content, after a fill | The "skip the read-back" path was used for a fill that does not actually cover the whole band. The band is written back whole on drop, so an over-permissive guard writes black rows. The guard must be evaluated in 64-bit arithmetic or extreme coordinates wrap into a false positive. | `emulator-core` |
| Frame budget blown and the log is flooded during idle | A tracing instrumentation attribute on a per-frame path. Instrumentation spans default to INFO, not DEBUG, so "set the level to info" does not fix it. A WIPI title idles on timers, so its timer callback is the worst possible place for a log record. Audit every per-frame log site before shipping. | `emulator-core` |
| Alpha-zero source pixels stopped repainting the background after a graphics optimisation | An accepted, documented semantic change on ARGB destinations — the previous behaviour was itself a bug. Bit-identical on RGB565, which is every path a feature-phone title uses. Pin it with an equivalence test rather than reverting. | `emulator-core` |
| The device is much slower than the headless run at the same frame count | Compare the work gauge (guest instructions per frame) first. If it matches, the cost is in your host layer — blitting, scaling, or per-frame allocation — not in the interpreter. A nearest-neighbour blit with a cached column lookup table and vertical run copying removes millions of integer divides per frame. | `android-host` |
| The whole game feels about half speed — every screen, not one — and the host worker's own gauge says it is idle most of the time | Two host layers each round the guest's timer period up to their own pacing grid, and the roundings multiply: an event pump that sleeps a flat interval when its queue empties, plus a worker that naps to "fill" the frame period, turned a 20 ms guest timer into a measured 45 ms. Never sleep past the guest's own next wake-up, and make the pump sleep only until the earliest not-yet-due timer. The frame pace is a ceiling on loop frequency, never a nap length. The symptom names one screen; the defect is global. | `emulator-core` |
| The game got faster after visiting one particular screen once — and faster again the second time | The timer-cancel primitive is a do-nothing stub while arming *pushes* a new shot instead of replacing the pending one, so every visit leaves a live frame timer behind and the frame callback runs once per live timer. Key shots by generation (arming and cancelling both bump it, the pump discards a stale key) rather than deleting from the queue, whose caller is usually a guest callback the pump is currently running. General rule: for every set/alloc/open/start you implement, audit its unset/free/close/stop — a no-op there is a leak, not a placeholder. | `emulator-core` |
| The player's in-game speed setting stopped mattering, or the game runs at exactly double the chosen speed | A host-side ceiling clamp on the guest's requested frame-timer period. On this class of title the frame-timer period **is** the speed option, so a flat cap rewrites every slower setting to the cap. Put a *floor* on the clamp, above the whole band the option can produce, so only out-of-band values (a modal screen's much longer period) are ever shortened — and keep the clamp a runtime switch, because it is a behaviour change, not an optimisation. | `emulator-core` |
| On a slow device the tick stops returning: input latency becomes unbounded and a backgrounded app keeps burning CPU | The event pump yields only when its queue is **empty**, and a callback that re-arms an already-overdue timer means it never empties — so the worker's input drain, its background-pause check and its frame pacing are all unreachable, and the executor's own deadline is only tested between steps. Bound due timer callbacks to **one** per poll and yield. On a device that keeps up the branch never fires, so the change is free. | `emulator-core` |
| One class of screen runs at 5–7 fps while ordinary play is fine, and the gauge says the host thread is idle there | The game itself arms a much longer frame timer in that state, and that is its design speed. Print the period the **guest asked for** (min/mean/max per interval) next to how long the host actually slept; if the guest asked for it there is nothing to optimise, and anything faster is a product decision about overriding a guest constant. | `emulator-core` |
| A specific effect — a flash, a skill animation, a fade — hitches for a few hundred milliseconds, and the periodic gauge looks completely normal | A 30-second aggregate dilutes a 100 ms hitch roughly 100:1, so every window looks the same. Add a per-tick over-budget report printing the **delta** of every counter across that tick, rate-limited to about one line per 400 ms (the log write comes out of the same frame budget). Read the guest-instruction delta first: millions means the interpreter, a few thousand plus a big asset or allocation delta means host work on that thread. | `emulator-core` |
| A hosted guest pixel loop leaves a half-drawn or half-tinted rectangle | Writes began before all reads had finished — including a runtime-built lookup table. Order every read before any write; then a refusal is safe at any time, including on a build where a table moved. | `emulator-core` |
| A hosted pixel loop's output shifts or clips wrongly near the screen edges | The guest function does no clipping at all — its caller clips — and the host clamped again. **Refuse, do not clamp:** every case outside the gate falls back to the guest and reproduces the displaced instruction exactly, so the worst case is the performance the build had before. Count refusals per cause. | `emulator-core` |
| The A/B frame hashes are identical and the hosted loop is clearly not helping | The hook never fired in that run, and a matching hash across a run that never reaches the code proves nothing. Require a fire counter beside the hash comparison, and prove firing on the device when a deterministic script cannot reach the state. | `emulator-core` |
| You hosted a guest pixel loop, shipped it, and the reported hitch is still there | There is more than one pixel loop, and the next one may take **no source pixels at all** (a per-pixel colour transform of what is already on screen), so every blit counter reads normal while it runs. Classify loops by what they *read* — opaque sprite blit, alpha rectangle fill, translucent/LUT sprite blit, tint rectangle — and expect each one you remove to uncover the next. | `emulator-core` |
| A narrow fill still costs a whole-band read, a whole-band write and an allocation | The covering-fill fast path only skips the **read**, and only for fills spanning the full framebuffer width. At 16 bpp, write the rectangle's own pixels: no band read, no band write, no allocation. Byte-identity is provable (the colour round trip is the identity across all 65,536 values) and should be pinned against the banded canvas, covering negative origins, both boundary overruns and zero extents. | `emulator-core` |
| A syscall or trap counter shows tens of thousands per second and the obvious subsystem gets the blame | The total names magnitude, not kind. On some carrier frontends the C standard library is dispatched through the same trap, so a total cannot separate a memory copy from a socket call. Two relaxed increments at the single trap entry point — a per-category array and a per-id array — cover every dispatch path. A published finding in the reference port blamed a receive-poll spin that measured **0/s** once per-id counters existed. | `emulator-core` |
| Half a day spent optimising a windowing or surface dependency's hot path that turns out to be already fixed | The tree vendors a fork of that crate through a cargo patch table, which is invisible in a normal read of the dependency. Check the patch table and read the **vendored** source before suspecting any dependency, and keep the *why* of each fork in the patch table's comment. | `emulator-core` |
| A static screen — a title, an open menu, a shop — burns as much host CPU as gameplay | The guest repaints on its frame timer whether or not anything changed, and every repaint rides the full convert/send/blit/present pipeline. Hash the **raw** guest framebuffer and drop the frame before the pixel-format conversion; count the guest frame before the skip so existing gauges stay true, and expose sent/s versus skipped/s — a zero skip rate on a static screen means the gate is dead. | `android-host` |
| An older phone gets hot after about ten minutes while a flagship never complains | Sustained load, not throughput. Decompose into three axes (interpreter, host pixel pipeline, synth) and remove **invisible** work: always-on identical-frame skip, an opt-in half-resolution render that the compositor upscales (dividing every pixel-proportional cost by four), and a cheap synth preset on the same switch. Ship it as a user-visible switch defaulted off, not a silent device tier. | `android-host` |
| Capping the frame rate to reduce heat makes the game run in slow motion | On this class of title the frame rate **is** the game speed: the guest advances its logic on its frame timer, and that timer is often the player's own speed setting. Never cap fps; reduce per-frame host cost instead and leave the guest's timing alone. | `android-host` |

> **REFUTED.** *"Maps with a lot on screen stutter because every draw call reads the whole
> destination framebuffer out of guest memory."* That is one of two causes, and it is the wrong one
> for a title that rasterises in its own guest code — which is the common case. **Refuted by:**
> counting platform draw calls per frame in the reference port: 12 draw calls per field frame,
> **zero** image blits, and 2.46 M guest instructions per frame. The framebuffer round-trip was
> charging almost nothing, because the game takes the screen pointer once and never asks the
> platform to draw a sprite again; hosting one guest pixel loop removed 36 % of all guest
> instructions with 7/7 identical frame hashes. **Why the wrong reading was attractive:** the
> round-trip cost is real, it is easy to measure in isolation, and it genuinely does scale with
> call count × screen area — on the titles that *use* the platform's draw calls. **Correction:**
> count platform draw calls per frame, per screen class, *before* optimising either layer. Many
> calls → the band work above. Few calls plus millions of guest instructions → profile guest PCs
> and host the guest's own pixel loop. Both answers occur inside one title.

### 2.4 Memory, allocator and long sessions

| symptom | what it actually means | skill |
|---|---|---|
| Steady-state stutter, and the allocator's header-bytes counter climbs into gigabytes | The bucket allocator's one-bit-per-slot map is being read in full on **every** alloc and free. Replace the bitmap scan with an 8-byte header holding a LIFO free-chain head and a bump index — but **keep an indexed in-use map**, because a bare free chain cannot survive a double free (pushing an already-free slot links it to itself and every later allocation of that class returns the same address forever). | `emulator-core` |
| Two live objects at the same guest address | Exactly the aliasing failure above. Leaking is survivable; aliasing is not. On a suspect free-chain head, log and drop the chain, then fall through to the bump index. | `emulator-core` |
| Allocated blocks leak "loudly" at free | A free whose size argument selects a different size class than the allocation did, so the address is not a slot boundary of the class being freed. Leak it and log it rather than corrupting the class. | `emulator-core` |
| The heap gauge's live count climbs monotonically during steady play | A guest-side leak. Note that some leaks are the *game's*: driving the game's own save primitives from the host allocates on each call and the game frees nothing, because the original only saved on demand. Mitigate with cadence, and say so in a comment. | `guest-re` |
| The interpreter thread overflows its native stack after tens of minutes | Instrument the thing that actually overflows, from outside the code that uses it — ask the kernel how much of the stack mapping has ever been resident. In-process nesting counters measured three plausible layers and cleared all three. Enlarging the thread's reserved stack is a mitigation, not a fix, and must be labelled as one: reserved address space costs nothing until touched. | `emulator-core` |
| The OS kills the app first among running apps, and an audio or asset handle count never stops climbing | A handle-minting platform call whose destructor is unimplemented: every upload mints a fresh handle holding its own copy of the data and nothing removes it. Track handles host-side keyed by the guest object pointer and release the bookkeeping on the guest's own free call. Do **not** read the handle back out of the guest's struct — the create call hands it back uninitialised, and closing whatever integer was sitting there can silence an unrelated clip — and do not stop in-flight playback on free, because overlapping effects are the game's own behaviour. | `emulator-core` |
| Process RSS climbs by tens of megabytes and the culprit is a vendored audio or asset library | Its loader deep-copies a read-only structure once per reference (measured at 9.7× the entries the file describes). Share it behind a reference count with a per-source cache, and prove the change invisible by counting the field's uses in the whole crate: read-only after load is what makes the parsed data, the rendered output and the behaviour provably identical. | `emulator-core` |
| After you make guest page commit lazy, freshly mapped guest memory is rejected as an invalid pointer | "Is this mapped?" was being answered from the presence of a page allocation, which stops being the same question once commit is lazy. Keep a separate mapped bitmap, one bit per page, as the only thing the mapped query consults — and keep the page array a fixed-size array behind a box so the index bound check still optimises away on the interpreter's hot path. | `emulator-core` |
| One small asset — a sound effect, an icon — costs milliseconds and shows up in the per-tick hitch report | The resource fetch re-reads and re-parses the whole archive per call, several times per fetch (measured: six full archive copies plus six directory parses per sound, 3.9 ms on a desktop host, on the emulator thread inside the frame budget). Cache resource bytes for the process, keyed by (application id, resource name) so two emulators in one process cannot read each other's resources, with a size ceiling whose overflow *stops* caching so the worst case is exactly the old behaviour. | `emulator-core` / `archive-prep` |
| Occasionally the wrong sound or the wrong asset is used, with no error at all | A parse-once cache keyed on a 64-bit hash alone. Confirm with the actual bytes before returning a hit. This failure mode is not a crash and not slow — it is wrong output, and it gets blamed on the emulator for months. | `emulator-core` |

### 2.5 Sound and music

Sound faults arrive in the player's words, not yours, and the same sentence usually has two
independent causes. Two of the rows below are cross-phase: the per-sound hitch is an archive
fault, the volume law is a core fault, the ducking is a host fault.

| symptom | what it actually means | skill |
|---|---|---|
| One tester's device has no sound at all, and you cannot reproduce it on any device you own | A single failed open of the audio output — a cold-boot race, another app briefly holding the device, a route switching — was treated as permanent, so one transient failure became a whole session of silence. Retry the open forever (fast retries for the race, then a slow patient loop), draining both event queues on every attempt so a long retry cannot accumulate a backlog that fires on success. Then write a human-readable status string at every stage of bring-up into an on-device diagnostics screen: that turns the next report into three cases — output open failed, instrument bank failed to load (music off, effects on), or open-but-silent (an in-game setting or the system volume). | `android-host` |
| The music is barely audible with the phone at maximum volume, and the volume keys seem to do nothing | Two independent causes producing one sentence. The bundled synth is running at its library default output gain, which is a safety margin for arbitrary many-voice music and not a mix decision for your content; and the volume rocker is not pinned to the media stream, so it moves whichever stream the system thinks is active — for a game that is often silent, the ringer. Render each music file offline at unity gain, tabulate peak and RMS, set the bus gain from that table, and let a limiter handle the one file that exceeds unity. | `android-host` |
| Music and effects are wildly different in loudness at the same in-game setting, and every attempt to balance them moves the problem to a different slider position | The two buses are being scaled by two different laws — typically linear on the PCM bus and note-velocity on the sequenced one. Velocity additionally runs through the instrument bank's concave velocity-to-attenuation modulator (roughly double the dB drop) and selects sample layers and filter cutoff, so the sequenced bus gets quieter *and* duller on a curve unrelated to the other bus. One volume law, one function in the core, applied as an **output gain** to both buses and curved (square the normalised level, or a linear map spends nearly its whole range in the top step). Let the sink declare whether it applied the level so nothing applies it twice. Success criterion: the measured gap between the buses is **constant** across all slider steps. | `emulator-core` |
| The music cuts out whenever an effect plays, and then **starts over from the beginning** | The guest owns exactly one sound slot: to play an effect it stops the music, frees and re-creates the same clip object for the effect, and afterwards re-issues the music from the top. Your host is reproducing that faithfully. "Starts over" is the giveaway — no level or masking problem can restart a song. Give the host its own music channel and **defer** a music stop by a grace period derived from the measured stop-to-effect latency, then decide from what arrives inside the window (an effect: hold the music open and overlap; the same song: cancel the stop and ignore the restart; a different song: the stop was real). | `emulator-core` |
| After you make the music survive effects, it now plays over a menu or a cutscene that should be silent | The deferred stop was simplified into "ignore guest stops". The guest also silences the music deliberately — one traced menu open produced a stop followed by 4.5 seconds with no sound call at all. Never ignore a stop; defer it. "Nothing arrived inside the window" is a real branch of the decision table and must honour the stop at the deadline, and the window must stay short enough that a genuine silence does not start audibly late. | `emulator-core` |
| Effects are inaudible only during certain songs, or only for a player who has raised every slider — and two handsets report the opposite problems, one "too loud" and one "too quiet" | A static limiter or waveshaper applied to the **sum** starves whichever signal is added last: once the music alone is past the knee, an effect on top is compressed away rather than mixed in (measured −5.9 dB at a music peak of 0.66, −20.2 dB at 1.18). A player on a quiet handset raises every slider and lands exactly on that operating point, so the effect bus is not quiet — it is being erased, and no global trim can fix it. Decide who gives way: duck the music bus while an effect sounds (start at −6 dB, ~12 ms attack, ~140 ms release) and keep the sum limiter as a rare-peak safety net. Verify that a default-settings mix is bit-unchanged, and do not duck deeper, or the music dip becomes the thing the player notices. | `android-host` |
| The music stays quiet after the last effect, or after the app has been in the background | A duck or fade envelope whose release only runs on frames that still owe a duck (so the bus parks at the ducked gain), and/or shared duck state expressed in wall-clock milliseconds and consumed by a render thread that legitimately stops consuming while backgrounded. Run the envelope every frame including when the owed amount is zero — that *is* the release — count the shared state in bus **frames** rather than milliseconds, combine overlapping effects with a max rather than a store, and reset the envelope to unity on entering the background. | `android-host` |
| A burst of noise plus a frame spike every time the app returns from the background or the screen unlocks | The sequencer sleeps only while the next event is in the future, but the host stops ticking the emulator while backgrounded and the platform clock keeps running, so the whole remaining backlog is dispatched inside one poll on the emulator thread. Re-base the timeline when the deficit exceeds a few hundred milliseconds — advance the start time by exactly the deficit so the current event is due now and later events keep their spacing — and compute elapsed time with **saturating** subtraction: a wall clock can step backwards, and an unguarded instant difference underflowed into an "elapsed" of millions of years. | `emulator-core` |
| A brief frame hitch every time a sound plays, worst on hits that play two sounds in one frame | Almost never the decoder — a benchmark over one title's whole sound directory measured 0.016–0.049 ms per effect. The real per-sound taxes were a synchronous platform service call issued inline on the emulator thread, and the archive resource path re-parsing the whole archive several times per fetch. Measure the whole per-sound chain before touching audio code, and put sound plays and parses in the line your host prints when a tick overruns. | `emulator-core` / `archive-prep` |
| Rapid effects arrive late and keep draining after the action that caused them has finished | PCM one-shots are being appended to a sequential player queue, so each waits for the previous one. Add each clip to the mixer as its own concurrent input; overlapping effects are correct behaviour, not a defect to serialise away. | `android-host` |
| The music resumes from the beginning, or the output device fails to re-open, every time the phone is unlocked | The background gate **stops** the audio sink. Stopping loses the song position and requires a re-open — exactly the operation that fails on the devices that had trouble opening in the first place. Freeze instead: the render source checks the paused flag once per chunk and emits a silent chunk without advancing the synth and without draining queued events, leaving the device open. Reset any time-based envelope state in that same branch. | `android-host` |
| A player on a new handset reports the opposite of the tuning you shipped, and changing the constant would regress the phone you already tuned | A single global trim chosen by ear on one device. Where one volume law serves both buses and only one bus additionally eats the trim, that trim is a fixed dB offset at every slider step — and the same headroom is not the same experience on two handsets. A third global number just moves the complaint to a third phone. Make it a setting whose default is **bit-identical** to the constant, at a fixed dB spacing, read at the point of use so it applies to the next sound with no restart, with an out-of-range stored value falling back to the default. Do not offer unity as the top step if any effect asset decodes to a full-scale peak. | `android-host` |
| A note in your own documentation says the title "does not use PCM audio" or "nothing ever stops the music", and both turn out to be false | A negative claim written from one device trace. Zero calls to an entry point in one recorded session means that session never triggered it, not that the title never does. In the reference port this cost weeks: every effect was PCM, and the guest stopped the music on every single one. Write "not observed in `<named scenario>`" and design the scenario that would trigger it before concluding. | [evidence-standard.md](evidence-standard.md) |

### 2.6 Host to guest: reads, patches and calls

| symptom | what it actually means | skill |
|---|---|---|
| A host-initiated guest call panics inside the JVM the first time it runs | See the PANIC row in §1 — the spawned task is not an attached JVM thread. | `emulator-core` |
| A guest call enters and immediately pops garbage into the program counter | The target is **not a function**. Jump-table arms share the parent's stack frame and exit through the parent's epilogue; some "functions" begin by reading the caller's frame. Verify before calling: the target must have its own push/pop prologue and epilogue and set up its own static base. | `guest-re` |
| A host state machine waits forever for a guest call that already failed | A two-state result cell conflates "not yet" with "failed". Use three states — pending / ok / failed — and give every step a timeout at roughly 100× the expected latency, reset per step. A backend with no CPU core must **fail** the result rather than leaving it pending. | `guest-re` |
| A patch works once, then stops after a new game, a load or a death | The patch is not being re-asserted. Read, compare, write only on mismatch, and re-run every frame. That single discipline makes every poke idempotent across all game-state transitions with no ordering logic, and makes expiry self-cleaning. | `guest-re` / `android-host` |
| The re-assert pass only works the first time | The helper compares against the pristine bytes only. It must also accept **its own previous encoding** as an already-applied state. | `guest-re` |
| A patched widget tears apart — half of it moves, half does not | Either you patched one of several immediates the widget uses, or the whole block **exists twice**: a compiler outlines an else-arm and reaches it with `bl` used as a long branch. Patch every site or none. | `guest-re` |
| Writing to "proven dead" guest code crashes the game | The reachability sweep did not follow `bl`. On Thumb-1, `bl` is routinely a long branch, not a call. A correct sweep follows `bl` targets, honours literal pools, and cross-checks direct branches, function-pointer words and jump-table bases. Guard the final address with a compile-time assertion so it cannot drift out of the proven range in a passing build. | `guest-re` |
| An assertion on a payload length fires on the very first real use | You pinned a measured value as an invariant. Serialised lengths are content-dependent. Assert a plausibility band, not a constant. | `guest-re` |
| A host-drawn indicator freezes on or off after a block-skip patch | The skipped block was maintaining that state (a blink counter, a frame index). Anything the skipped code updated is now frozen; the host must use its own clock instead of reading the guest's flag. | `guest-re` |
| A timed host feature silently never fires | A sentinel bug. If "never armed" is encoded as `0` and the check is `now >= last + interval`, then treating `0` as "now" makes the comparison false at **every** poll. Encode "never armed" as a distinct hard case and seed it at session start. | `android-host` |
| A feature's button always reports that it cannot be used here | The control is only reachable in a state the gate refuses. Prove the control is reachable in a state that *passes* the gate — a state machine can be correct and still unreachable. | `android-host` |
| A host feature reads a plausible number out of a stale pointer | Validate every pointer hop against the heap window and sanity-ceiling any size derived from guest memory *before* allocating on it. A stale handle must yield "no data", never a render of garbage. | `android-host` |
| The host reimplementation of a guest widget is subtly wrong and nobody notices | Diff it. Run both in the same process and compare pixel for pixel, with your output quantised through the same colour round-trip so the comparison is like for like. Zero mismatched pixels on two different game states, or it is not verified. And the check must exercise the shipping source — see [selftest-convention.md](selftest-convention.md). | `android-host` / `guest-re` |
| A diagnostic that should be reporting prints nothing | Many diagnostics are gated on an explicit frame list. A gate that silently produces no output is indistinguishable from a clean result. State the gate in the tool's own help text. | `guest-re` |
| A host write lands at an address you have proven correct and nothing happens | The value's *shape* is wrong for how the guest **reads** the field — commonly a byte the reader sign-extends and tests as `< 0`, which a value of `1` can never satisfy however right the address is. Disassemble the reader, not the writer, and make the anchor a triple: offset, value, and the reader's predicate. An offset-only entry hands the next porter the half of the fact that does not work. | `guest-re` |
| Several sessions each measured a different value for "the same offset", each looked right at the time, and none works reliably | The offset is not a constant: it is an element of an array indexed by a live word elsewhere (a slot number, a page, a tab), and each historical measurement is a different element. A literal or displacement sweep reports zero sites, because nothing materialises the final address. Copy the game's own address arithmetic verbatim, including the index load, and **reject** an out-of-range index rather than falling back to element 0. | `guest-re` |
| A static search for the constant the game must be storing returns zero sites image-wide | Zero hits is the most misread result in this work. The compiler may have synthesised the constant instead of emitting it (a small immediate plus a negate, a reciprocal multiply for a divide, shift pairs for large values), or the address may be computed at runtime so no literal names it. Treat a null scan as "my search cannot see this", never as absence; do not flip a shipping table to unsupported on that inference; and write the search's blind spot down next to the null result — in the reference port that one sentence was the next session's starting point. | `guest-re` |
| You searched the region the other build put the field in, found a candidate whose offset, value and timing all matched, and the host write does nothing | A watch window centred on the expected answer can only confirm or mislead — it always yields a best-in-window candidate, so it never reports failure. Three consecutive wrong answers came out of one 128-byte window. Watch the whole record and the whole static area (tens of kilobytes twice a second is a memcpy), auto-mute bytes that change on consecutive samples (they are counters and they bury the signal), and accept an answer only when the host writing that value reproduces the **effect** — "it changed at that instant" can be a block write moving a neighbour. | `guest-re` |
| `xref`/call-graph tooling reports no callers for a function you have strong evidence is called | The image routes cross-module calls indirectly: load the biased target into a register from a literal pool, then branch-and-link to a one-instruction veneer. A branch-and-link scan attributes everything to the veneer. Search for the biased literal word instead, and resolve each call's real target by computing the pool address and reading the word. Detect the pattern once per image: a veneer leaf with an absurd call count. | `guest-re` |
| Two investigations disagree about which function a given call reaches | Both are reading an indirect call and inferring the callee from context, and two readings of one instruction are not two derivations. Compute the literal-pool address, read the word, and enumerate every site in the image that loads it. | `guest-re` |
| A dispatch table or constant table cannot be found anywhere in the image and appears to exist only at runtime | It is in `.data`, and static tooling that maps only the code section linearly cannot reach it. Read the ELF section headers for the data section's file offset and virtual address and dump the table from the file. The BSS section legitimately lies past end-of-file. | `guest-re` |
| Guest text you patched at runtime never changes, and no error appears anywhere | The "is it already patched?" guard compared only a prefix of the replacement, and the replacement sentence begins with the same word as the original — so the guard matched the **original** and the write never happened. Compare the whole replacement, and record the incident at the comparison. | `guest-re` |
| You cannot get the sentence you want by editing any single string in the image | The sentence is assembled by a formatted print from a format string plus several literals. Write the whole replacement into a spare tail literal and repoint the literal-pool **format pointer** that the call sites read; with no conversion specifiers left the surplus arguments are ignored. Check first that all call sites read the same pool word. | `guest-re` |
| A binary-patch hook installs cleanly, passes its expected-bytes check, and fires zero times | The site computes the right value but is not on the path your feature takes. Verifying the original bytes proves only that the instruction is at that address. Verify the call graph before placing a hook and the fire count after — log a counter and compare it against a sibling hook in the same session. | `emulator-core` / `guest-re` |
| A host feature's change works and is gone after the app is killed | The mutation was made from a menu, and the game's own save gate requires the field/world state, so nothing was ever written where the change happened. Arm the same deferred-save retry a consumable item uses and let the worker fire it on the first poll that passes the game's own gate. | `guest-re` / `save-integrity` |

### 2.7 Live game data: caches, snapshots and containers

The rows in [§2.6](#26-host-to-guest-reads-patches-and-calls) are about reaching guest memory at
all. These are about what you find when you get there: the same number stored in three places, and
containers that move records under your feet.

| symptom | what it actually means | skill |
|---|---|---|
| A host write into a game record has no visible effect, but the number becomes correct the moment the player equips the item, changes screen, or reloads the save | The field the screen shows is a **derived cache** computed from the raw bytes you wrote, and exactly one guest routine rebuilds it — equipping and loading work because those paths run the rebuild. Call the game's own rebuild rather than recomputing host-side, and first enumerate that routine's **stores**: if the field the screen shows is not among them, you are rebuilding the wrong cache and there is a second copy. | `guest-re` |
| A displayed value is still stale after you correctly called the game's own rebuild over every record | There is more than one copy. Screens are commonly fed a byte-for-byte whole-record **snapshot** baked into a separate array at a state change (equipping, opening a page), while the rebuild you called writes only a couple of words in the record itself. Enumerate writers, readers **and whole-record block copies**, searching for the same relative field offsets under a different base — that is the snapshot signature — then also call the routine that re-bakes it, usually at the tail of the state-change routine the player's own description names. | `guest-re` |
| A host mutation occasionally lands on the wrong item — the player picks one thing and a different one changes or is consumed | The game **compacts** its containers, swapping whole records between cells, and the compactor's wrapper is reached from many places including the item popup's own close path. A (container, slot) pair is not an identity. Re-match both ends at commit on the record's own instance key — the field the game's save or protocol keys on — and refuse silently on a mismatch. A zero key must match nothing, including another zero. | `guest-re` |
| An asynchronous host-originated rebuild refreshes the wrong object's data | The call was queued with a cell captured before a compaction and executes a tick later, by which point another record occupies that cell. Do not chase the cell: run the rebuild over the whole container after the compaction has happened. It is a pure function of each record's own bytes, so it is idempotent — it is what the save loader does on every load. | `guest-re` |
| An entire item or object category is missing from a host-built list, and no greyed "why" row appears either | Two faults compounding: the game's own validator was **upper-bound-only** and your reimplementation added a lower bound, and the category filter runs *before* the row builder so the rejection produces no visible row. Re-disassemble the cited gate and transcribe the comparison exactly, including the half that is absent, then check that the host UI, the offline engine and the tests all denote the same set. | `guest-re` |
| The report arrives as a question about game design — "can this item type not be upgraded?" — rather than as a bug report | A silent host-side pre-filter. "My item is not in the list" is indistinguishable from "the game does not allow it". Never drop a candidate silently: list it disabled with the reason on screen, and treat any pre-filter that can remove a player-visible item as a defect. | `guest-re` |
| The HUD, quick bar or other host overlays disappear when the player unequips a piece of gear | A plausibility gate inside the state resolver — current ≤ maximum — that ordinary play violates, because equipment carries the maximum and removing it drops the maximum below the current value, so the resolver reports "no object". Keep only the tests that reject a not-yet-created record, and clamp gauges when **drawing** them. A gauge reading high is never evidence that the object does not exist. | `guest-re` |
| A host refresh sweep runs on schedule, reports zero objects, and never fixes anything | The state resolver refused mid-transition and the sweep spent its retry budget on an empty read — and the transition is often produced by the very action that needs the sweep. Treat an empty sweep as a failed read rather than as a valid answer: retry without consuming a pass, and re-trigger on the edge of entering the screen that reads the data. | `guest-re` |
| Using one unit of a stackable item consumes the entire stack | The container cell holds a stack and the code operated on the cell. Decrement the count; clear the occupancy byte every guest reader gates on only on the last unit. Never compact the container yourself — that moves other items under the player's cursor. | `guest-re` |
| A value the host wrote into a record causes garbage or a crash on every subsequent launch, not just once | The load path re-derives from that field through an unchecked table index, so the bad value is reproduced deterministically forever. Bound host-written ids yourself — the game does not — and refuse a record whose own fields contradict each other rather than repairing it. | `guest-re` |
| Two adjacent same-typed byte fields in a record behave as if swapped | Code that treats them symmetrically cannot distinguish them, and both readings look correct. No amount of disassembly will decide it: settle the roles on a live record whose two values differ, from a device or a probe run. | `guest-re` |
| A published probability or reward table disagrees with the shipping calculation by a tenth of a percent | The table was derived by hand and truncated where the implementation rounds. Verify by exhaustively simulating the die over every reachable input — an inclusive uniform die makes this a small enumeration — and let the simulation decide which of the two is right. | `guest-re` |
| A host overlay prints a confident number over the wrong step of a multi-step flow (odds over the item picker, a cost over the result screen) | The overlay is gated on the window or screen id, which stays constant for the whole flow, while the flow's own epilogue resets a separate step byte. A screen id is not a step id: gate on the byte the epilogue writes and pin the two distinct step values in a test. | `guest-re` |

### 2.8 Save data: loss, slots and restore

The highest-severity class in the whole port, and the one a player reports in the fewest words.
Start here for anything of the form "my character is gone", "my slot says empty", "my items came
back wrong" or "it stopped saving". Owner: `save-integrity`.

| symptom | what it actually means | skill |
|---|---|---|
| "My character shows as an empty slot, and after restarting the app it is completely gone" | A deletion or truncation event — never corruption. The guest's slot list can only report "empty" for a missing, zero-length or checksum-failed record, and its summary builder cannot express failure at all, so a damaged save still loads. Stop debugging the serialiser. Candidates in order: a create-mode open truncated the record up front; a failed write left a deferred truncate armed and close executed it; a non-atomic replacement left the file zero bytes. | `save-integrity` |
| One save slot's character has been replaced by another slot's character | The slot index in the record name is a slot-**list cursor**, not the loaded character's identity, and the game never unloads the character — so merely navigating the slot list re-aimed every later save. Gate writes and deletes on a pin whose only source is an **observed character load**, and redirect proven writes to the pinned slot. Never patch the guest's cursor: the slot screen breaks and you have moved the bug, not fixed it. | `save-integrity` |
| Saves stop persisting after the player visits an online or storage screen — a withdrawn item vanishes after a restart, a deposited one duplicates | A storage-layer guard is silently refusing writes: the guest ignores the write's failure code while host-owned files have already committed, so the two diverge. Commonly the guard was armed only "while in play" and those screens share the shell application state, so the pin was never latched at all. Replace refusal with redirect where the owner can be proven, check what the arming condition excludes, and grep the log for the refusal verdict during the flow. Diagnostic tell: two unrelated-sounding reports ("it does not autosave" and "items vanish when withdrawn") from one root. | `save-integrity` |
| You guarded the destructive path, verified it against the reporter's exact reproduction, shipped it, and the same data was destroyed on the next build | There were two paths producing the event and you guarded one. The second produced no network frame and no host-visible call, so it was invisible to the signal you chose. Enumerate the **readers** of the primitive rather than the senders of the frame you noticed, pick a signal every path must pass through, and validate the new signal against an existing device trace with the counts stated: every occurrence a true positive, zero false positives. | `save-integrity` |
| A save-integrity fix passed all its tests, shipped, and destroyed a save anyway — for the third time | The guard trusts one scalar (which slot the live character occupies) completely, so every clause you add is downstream of a wrong input, and each attempt added a clause instead of fixing the scalar's provenance. Make provenance the invariant: the scalar may only be written by an observed load, enumerate every load path first, and leave a tombstone naming every rejected source and what it cost. | `save-integrity` |
| A host state pin is frozen on one value and silently approves everything, and the log shows it was never re-stamped | The pin was taken on a **proxy** edge — the socket opening — which happens once per session, at an instant when a menu entry has just reset the cursor to zero. The pin could structurally only ever hold that one value. Before trusting a proxy signal, ask its cardinality: once per session, or once per action? Take the signal from the observed event itself and re-stamp it every time the event occurs. | `save-integrity` |
| Your safety check compares an identity field and always matches, especially for the users who report the problem | The field is not per-instance. Its single writer is called from world initialisation and indexed by a class byte into a class-name table, so it is a *type* name — and it is zero in any session that never initialised the world. Verify what writes a field and what indexes it before making it a safety predicate. Where no per-instance identity exists, do not tighten the policy with an identity check: that buys nothing exactly when it matters and re-buys the silent-no-write bug. | `save-integrity` / `guest-re` |
| Saves stop being written entirely shortly after you add a guard against writing to the wrong place | A refusing guard converts data loss into a silent no-write, and the application does not retry. One screen that resets the cursor your writer reads can disable every save for the rest of the session. Where the correct destination is derivable, **redirect**; keep refuse as the fallback for when the redirect's gates are not all satisfied. | `save-integrity` |
| A data-safety guard is correct as written and provably never fired on the path where the damage happened | The load-bearing condition lives in a caller, in a third file, so no test in the suite can reach it — and in the reference port that condition also happened to exclude an entire application state. Move the whole verdict into one pure function in one dependency-free file (`verdict(facts)` returning allow, refuse, or redirect-to-destination) and let callers only gather facts. Do not scatter the decision again; that is the whole mechanism of this class of incident. | `save-integrity` |
| A player's live character was reset to an old, partial version right after entering an online screen (reported as story, equipment and items all reset) | A dual-use request opcode: the login sub-request and the destructive restore request are byte-identical, the client's restore handler has no occupancy check, and the reply is deserialised over the loaded character. The fragment carries equipment records only and is whatever was last uploaded, so story and inventory vanish and equipment reverts to a stale snapshot. Guard on the **client** side — your host owns the record store, so it can answer "is this slot occupied?" — and **rewrite** the outbound frame into the sibling sub-request of the same fork. Dropping it hangs the client's wait state. | `save-integrity` / `server-revival` |
| The player's in-game exit button does nothing, so they force-swipe the app away | Treat it as a save bug: a force-swipe kills the process inside the truncate and non-atomic-write windows. The platform exit hook is often a log-and-return stub, and on some runtimes the guest's quit does not arrive on the documented exit call at all but as a constant selector on another kernel call the fork stubbed to return zero. Find the stub that fires exactly once at the quit confirmation and never during boot, title, load, play or save, then wire quit to a bounded final save followed by a real teardown. | `save-integrity` / `emulator-core` |
| The "restore an older save" feature ate the player's backup history — after one restore, fewer generations remain and the restored one is gone | Three costs nobody budgeted: the pre-restore pre-image spends a retention seat, the rotation it triggers runs over the same directory and can delete the generation being restored, and the first save afterwards archives a byte-identical duplicate (the rate limit cannot suppress it, because a boot-time restore runs before the emulator exists and the last-write timestamp is still zero). Pin the restored generation in a sidecar whose name the generation parser cannot match, hold it outside the retention tiers, and decline a pre-image that byte-matches the pin. | `save-integrity` |
| A restore appears to work, then the old data is back a few seconds later, or the record is half-replaced | The restore was applied while the game was running. The record may be open with its contents mirrored in a guest-heap buffer, and the next write-through snapshots that buffer back to disk. Apply restores at the **next launch**, before the guest opens any database: the dialog writes a request file, the app closes itself, boot consumes the request — deleting the request file *first*, so a crashing restore cannot loop. | `save-integrity` |
| The player-initiated "reset this slot" wiped a character with no archived copy, though the vault covers every other write | The guest's reset maps to a whole-**database** delete (a recursive directory removal), not to the per-record delete the vault hooks, so the one irreversible action had no archive behind it. Audit every host path that can remove a record, archive every record in the directory before a recursive delete, and exempt deletes from the vault's rate limit and identical-content shortcut — a delete's pre-image can never be re-taken. | `save-integrity` |
| The "your save is missing but recoverable" notice has never once appeared, even with a populated vault | The boot check read a remembered path that is only populated after this process writes a record, and its only caller is the boot check, which runs first. There is no error — just an absence. Give the boot check the same fallback directory scan the listing uses; that is precisely the case that matters, a player opening settings at the title screen to recover a slot. | `save-integrity` |
| You cannot get a player's save data off their phone to diagnose a loss | A release build is not debuggable, so a shell cannot read app-private internal storage, and the records are encrypted anyway. Add a player-triggered export of the vault (ciphertext only) into the app-specific external directory, and name each generation `<zero-padded-unix-ms>-<length>.bin`: a directory listing alone then gives you when, which slot, and the direction of the damage — a length jump is "this slot became different data at this minute", which attributes it to a build. Never tell anyone to uninstall; that destroys the saves and the vault together. | `save-integrity` / `port-shipping` |
| A "saving, please wait" panel looks broken — pressing its button does nothing | The panel deliberately swallows all input (that is its job: it freezes the screen that could re-aim the save) but was drawn with the same answerable confirm band as an ordinary message box. Draw a variant with no button at all. Separately: release the freeze on three conditions (quiet after the last write, a shorter empty timeout, a hard cap), and test a more specific modal **before** the save lock in the key path, or the notice becomes uncloseable. | `save-integrity` / `android-host` |

| symptom | what it actually means | skill |

| "A control keeps getting pressed by itself" while the player is steering | A second finger slid over a control and acquired its key. Only touches that **started** on a control may change key by sliding; track that eligibility in its own identity set. | `android-host` |
| A key repeats forever after the app is backgrounded, rotated, or the layout editor is opened | Held keys were not released when input routing changed. | A brief frame hitch every time the phone vibrates | Attaching a thread to the VM, looking up the system service and making a synchronous binder call, all inside a 16 ms frame. Move haptics to a dedicated, permanently attached thread. | `android-host` |
| An orientation toggle or a dialog silently does nothing, with a completely clean build | Native code looks the class up **by name** over JNI, and the runtime context handed to native code is the Application, not the Activity — a native thread's class lookup cannot see application classes. | A save survives a normal exit but not a task kill | The storage layer is asynchronous. | Pressing between two on-screen controls triggers an unrelated action, and the code arm that implements that action is not the one running | A whole-window virtual-stick zone is the real intake for every near-miss, so anything hung off "a short press in the stick zone that never latched a direction" fires on every imprecise tap — including a tap-to-move fallback, which is how "tapping between buttons walks my character there" happens. | Taps do nothing in a region where no control is drawn | A hit zone outlived the drawing that explained it: only the drawing was gated off for a mode. Gate drawing and hit-testing with the **same** predicate — an undrawn zone is an invisible control, and it will eat the tap meant to restore the controls. | `android-host` |
| Enlarging the virtual stick makes walking start noticeably later | Not a bug: the drawn ring radius **is** the deflection radius, so the thumb pins to the rim at full tilt. Keep the coupling and pin the trade-off in a test; if the maximum feels too far, add a stick-specific size cap rather than decoupling the two radii. | `android-host` |
| After a second touch mode shrinks the stick's zone, both the engage distance and the stick's own seat scale wrongly | A helper computed the deflection radius from the **zone's** width and height while meaning the **window's**. It was correct only while the zone happened to be the whole window. Audit every `(w, h)` argument in HUD code for which rectangle it means: window, game rect, control rect or zone. | `android-host` |
| Pressing near the corner of a direction control walks in the perpendicular direction | The direction hit areas are the edge-centre cells of a 3×3 grid with a cross-axis stretch, and the corner cells collide once the stretch exceeds about 1.4×. Tile the square into four bands instead, so non-overlap is a definition rather than an inequality. | `android-host` |
| A control set flashes for one frame between pages of dialogue | The transient guest state was detected with a deadline, or with a hold carrying an "if the world looks free, cancel early" clause — and the in-world predicate is **true** during the page-turn blip, so the cancel fires exactly when the hold was needed. | A newly added boolean changes which controls exist, but the control the player presses is unhittable until something else forces a relayout | The flag triggered a redraw instead of a relayout. | Tapping the key hint the game itself draws on screen does nothing, or does the wrong thing | Nothing claimed that region, so the tap fell through to whatever policy sits at the end of the chain — often *almost* right (advance one page), and therefore hard to notice. | Two controls exist for the same action — the game's own glyph and a host button elsewhere — and the player reports the wrong one as broken | A host control was kept after the game's own glyph became tappable. | In the layout editor, a tap meant for the visible control selects a hidden alternative control instead | Two alternative controls share one id set (correct), but the editor's hit test did not apply the same visibility filter the renderer uses. | A modal opened by a key answers itself immediately, at its maximum value, without the player pressing anything again | Android delivers move events continuously for a finger that is merely resting, and a slide-eligible finger re-enters the key-edge function still holding the key it already holds — so the very key that opened the modal is re-delivered as a press on the next jitter. | A user interface element vanishes intermittently, and the player reports that opening and closing a menu brings it back | The interface is acting on a guest value that was never measured in the field. | A boot-time notice about a recoverable state reappears on every launch | It was raised for a condition the player cannot act on from the notice itself. | A black band remains along one screen edge on a modern phone, even with the system bars hidden | The default display-cutout policy stops the window at the cutout's safe area, and the game surface is sized from the window, so the game stops there too. ### 2.10 Touch-driving the game's own menus

A keypad-driven guest UI can be made touchable without patching the game: write the game's own
cursor byte and synthesise its confirm key. Everything below is a way that translation goes wrong,
and several of them are destructive, because the guest's own action popup is one confirm away.

| symptom | what it actually means | skill |
|---|---|---|
| Tapping an item in the game's own menu immediately opens its action list (use / drop / detail) instead of selecting it | The tap handler writes the cursor byte **and** synthesises the confirm key in one gesture — which is the guest's own "confirm pressed twice", so the focus step does not exist and the player cannot look before acting. Split it: the first tap writes the byte and sends no key; a second tap on the already-focused target sends the key and writes no byte. Decide which by reading the cursor byte back from the guest, never by remembering what you wrote. | `android-host` |
| A tap in one window focuses the wrong item, and the game draws no selection box while showing another item's details | One screen's item-grid geometry was applied to another. Grids that share a cursor byte can have different pitches with identical cell sizes, so a tap resolves to an out-of-range index and the guest draws no cursor at all. Derive origin, pitch, columns and rows from the game's own drawn empty-cell frames on **every** tap — taking the pitch as the minimum gap between runs, with the others required to be multiples, because the selected cell's frame is covered by the highlight and one run is always missing. | `android-host` |
| In a shop, smith or crafting window, tapping anywhere inside the panel behaves like pressing confirm — sometimes completing a purchase | Three independent causes, all observed: a held "a scene is playing" flag survived into a window opened from dialogue, so a tap-anywhere-advances affordance was still live; the shared list widget's row count is stale, so any point resolves to row 0, which is the row the game pre-focused; or a variable-length grid's maximum item count was an arbitrary number, so the derived grid claimed the whole panel height. Cancel the scene hold when the window id becomes any *other* real window, allow-list only widgets you have watched drive that screen, and derive a maximum count from "does the block still fit inside the container". | `android-host` |
| With the host's pull-out keypad open, a thumb that misses a key opens a game menu row | Your overlay is centred on the window, which is exactly where the guest centres its own fixed-size panel, and the overlay's inter-key gutters and empty cells pass an exact-rectangle hit test. Add an explicit "this overlay is not open" term to the panel router's gate, for every host overlay drawn in the guest panel's region. Chain order alone does not close it — the overlay has no rectangle there to claim. | `android-host` |
| A second tap meant to pick a different item instead uses or drops the currently focused one | The guest's own action popup is open, and that state still reads as "an overlay screen plus an item page" in memory. Without a gate the tap moves the cell cursor and then hands the popup a confirm — and the popup's first row is the destructive action. Refuse the whole tap when the guest's popup-open byte is non-zero: this is where the irreversible actions live, so it must be a hard refusal rather than a re-route. | `android-host` |
| Touch works everywhere except on one family of screens, and the router's own log says the state gate refused them | An application-state word means two unrelated things — typically a title/slot shell **and** a family of network or sub-mode screens — and the gate treats it as "out of world". Discriminate on the **liveness of a record** (does the god object resolve to a real character), not on the state word. Then grep your own codebase for other gates using that constant: if one of them depends on it meaning the opposite, one of the two is wrong. | `android-host` |
| A tap writes a cursor value the game itself can never reach, and an unreachable screen opens — usually without crashing | The guest's range clamp on that byte lives only inside its key-handler arms; the commit arm loads, increments and stores with no bounds check. Clamp your own writes twice: in the pure geometry function, which must be incapable of answering outside the grid, and again where an index becomes a write. | `android-host` |
| A tap on a page other than the first corrupts an unrelated field of the same record | The cursor is an **array** indexed by another live byte (a page or a tab), so an out-of-range index does not write a bad value to the right field — it writes a good value to the wrong field. **Reject** rather than clamp when the index exceeds the game's own count for that array. Clamping an array index is the opposite of a safe default. | `android-host` |
| Menu taps work under injected taps but feel broken in a real hand — most taps do nothing | The press/release comparison is by coordinate, and tap slop is tens of window pixels, which is several logical pixels, so an ordinary tap's release is rarely the exact pressed pixel. A scripted `input tap` lifts at the same pixel, which is why the device test passed. Compare the two decisions by **meaning** — a badge must still be that badge, a panel point need only still be a panel point — act on the press coordinates, and test wobble with `input swipe` over a few pixels. | `android-host` |
| After a host-synthesised confirm, a key repeats forever with nothing on the screen | The synthetic press was inserted into the held-key / auto-repeat map. That map exists for keys a finger is holding; nothing is holding this one, so nothing will ever release it. Emit host-synthesised keys as an immediate down-and-up straight to the guest and keep them out of the held map entirely. | `android-host` |
| A host dialog drawn over a guest confirm dialog cannot commit — the underlying button never gets pressed | The host dialog swallows the confirm key unconditionally. Swallow confirm only where the guest is waiting on **you** (you are holding a reply it is blocked on); where a guest button underneath must still receive it, let the key through and latch whatever host state you need *on* that key event, because there may be no guaranteed window afterwards. | `android-host` |
| A pixel detector claims a target on a screen where the game drew nothing, or reports garbage right after a rotation | Missing fail-closed guards. Five belong on every detector: reject a frame whose length does not match width × height, require a minimum ink count, require a measured band-height range, classify only inside measured bands and ignore everything between them, and clip the grown hit target inside its container. | `android-host` |
| A pixel detector for one widget fires on a different widget that happens to share its colour | The detector matches on colour alone, and two unrelated widgets commonly share a palette entry — a selected button's background and an arrow glyph, a message box's grey band and a two-button dialog's. Discriminate on a shape invariant (run length, ink width, centredness, fill ratio) and write into the guard **which rival widget it exists to exclude**. That comment is what stops a future maintainer loosening it to "fix" a miss. | `android-host` |
| "Why doesn't touch work on this screen?" is answered by guesswork, and each guess costs a build and a device session | The decision is split across two threads with disjoint visibility — the frame buffer is on the UI thread, guest memory is on the worker — and only one side prints a diagnostic, so it is silent about exactly the half that failed. Print one verdict line per side, per interaction: the UI names which detector claimed the point or which gate refused it, with every gate's live value; the worker names the byte it wrote, or why the point was neither a row nor a cell. Log inside the guest's panel only, or stray world touches drown it. | `android-host` |

### 2.11 Gamepad and input sources

A physical pad is a second input device, not a second key source: it arrives on a different
Android path, it has its own release semantics, and it makes every host modal answer the question
"what does this device do here?" all over again.

| symptom | what it actually means | skill |
|---|---|---|
| Pad buttons work but the analogue stick produces no events at all | The bundled native-app-glue's default motion filter discards every motion event whose source is not the touchscreen, and the glue exposes no API to replace that filter. Capture the axes in the Java Activity (generic-motion dispatch, joystick source) and push them to native code over JNI. Do not try to swap the glue's filter. | `android-host` |
| The character teleports, or the HUD reacts as if the screen were being touched, whenever the stick moves | The joystick motion was forced through the windowing library, which treats every motion "move" action as a touch and delivers the stick's −1..1 axis values as touch coordinates. Do not route axes through the windowing library at all. | `android-host` |
| A hardware keyboard suddenly types quick-slot digits, or the phone's own back key stops working, after pad support is added | The Java source check used "any bit of the mask is set". Input source classes share bits — the button class bit in particular — so the test also matches keyboards and the device's own keys. Use the full-mask idiom and let every non-matching event fall through untouched. | `android-host` |
| Two of the shoulder buttons do nothing on a Bluetooth pad, while the others work | Many pads never send trigger key events: the triggers exist only as analogue axes, and which axis pair carries them varies between vendors. Read both candidate pairs, take the larger, threshold with hysteresis (engage high, release lower), and feed the result through the **same** mapping table as a synthetic keycode, so remaps apply to it. | `android-host` |
| A pad-held walk direction repeats forever after the player takes a call or opens the notification shade | Once the Activity loses focus the Java dispatch stops, so the release for a held pad button never arrives. ### 2.15 Server-side game rules: deliveries, refusals and holds

Once the transport works, the remaining server faults are about the *client's* rules: what it does
with a quantity you chose, which side is expected to deliver an item, and what a refusal has to
look like. Every one of these is a client-fidelity question, not a protocol question.

| symptom | what it actually means | skill |
|---|---|---|
| Items silently disappear during a storage transfer or a shop delivery — no error anywhere, and only for players whose inventory is nearly full | You authorised a quantity using a "total free space" model. The two sets coexist in one install; neither was deleted. Tell the player the other build's saves are invisible, not lost, log the resolved database name and namespace at open time so a report is one grep, and never change the namespace after release. | `port-shipping` / `save-integrity` |
| A host patch written for the second build passes its byte verification and the widget only half moves | The compiler outlined the block, so the widget's coordinate immediates exist in two byte-identical copies reached by different paths — and site counts are not portable between builds either (one build had 12 sites for a widget, the other 10, because two of its draws are shared by both paths). After finding one site, enumerate the rest before writing a line, patch the whole widget or none of it, and assert the count and the constant multiset per build, plus that no address appears twice. | `guest-re` |
| An offset believed portable between two builds reads a live but unrelated field, and only one code path misbehaves | Most struct offsets survive a carrier recompile; not all. Four counterexamples in one record in the reference port: a state byte moved back one word, and three fields in the high region moved by different displacements. Never introduce an offset on a new build without a live read: print known-good anchor fields next to the suspects, and if the reference block matches the on-screen numbers while only the suspect disagrees, that one offset shifted. Track "on but unverified on this build" as a distinct state from "gated off" — it produces wrong values, not absent ones. | `guest-re` |
| On the second build a host overlay feature has literally never drawn once, and the drawing code is provably present and un-gated | An upstream liveness gate changed meaning when the anchor **kind** changed. A pointer anchor can be null-checked; a static one cannot, so "is a character loaded" has to be judged by record *contents* — and any screen that legitimately has no character then fails that test. Separate "give me the anchor address" from "is there a live record", and audit every gate that transitively calls the resolver when you add a static-anchor build. | `guest-re` |
| A host-side guard duplicating one of the game's own checks blocks a whole feature on the second build, and the failure is asymmetric between two item classes | The guard exists only because build A's commit path **bypasses** the game's own input router, so the host had to re-implement the router's refusal; build B commits by synthesising an ordinary keypress, which rides the router, so the game applies its own check and the host's copy adds nothing except a read of a guessed address that now names a different live field. Make the guard's presence a coupling to the commit shape and pin it in a test. The asymmetry between two classes through one rewrite machine is itself the diagnosis. | `guest-re` |
| Two deterministic probe runs meant to isolate one changed word produce an empty diff | The two runs never actually diverged — the input you varied hit a wall or a clamp and both ended on the same screen. Compare **frame hashes before diffing memory**: an identical frame hash means the experiment failed, not that the field does not exist. And prefer diffing the static area over the heap on an absolute-addressing build, since most heap diff hits are framebuffer or tile pixels. | `guest-re` |

### 2.17 Process death: crashes, OS kills and hangs

Three different faults with one player report — "it closed and came back at the title". They are
told apart by *which device record* holds the evidence, not by reading your own log.

| symptom | what it actually means | skill |
|---|---|---|
| The app closes and comes back at the title after the player switches away and back; there is no tombstone, no crash log and nothing in the app's own log | The operating system killed the process for memory. Read the **process-exit history**, not the tombstone directory: a low-memory reason code and the resident size at death are the evidence. The usual cause in an emulator is a memory mapper that commits every page of a mapped range up front, so initialising the guest heap commits and zeroes the whole thing before the first frame and makes this process the fattest on the phone. Make commit lazy — allocate on first **write**, and return zero for a read of a mapped-but-uncommitted page without committing — and add a committed-pages gauge so a regression is visible as a number climbing back. | `emulator-core` / `port-shipping` |
| Native crashes stopped on the date your fix was installed, and players keep reporting that the app closes | Two unrelated faults presenting identically. One axis (the crash) is closed; the other — an OS kill, or a hang — leaves no tombstone at all, so a tombstone-only investigation sees nothing and concludes the fix failed. Cross-tabulate three device records before drawing any conclusion: the tombstone directory for crash detail, the system crash-log store for timestamps that survive reboots (it dates the last crash, and so proves whether the fix landed), and the process-exit history for deaths with no crash. Attribute each record to an installed build before comparing. | `port-shipping` |
| A crash report from a shipped build is a list of hex addresses; the shared object inside the distributed package is stripped | Release artifacts carry no symbols, and rebuilding a debug artifact to get them changes the binary and often the bug. Symbolicate the stripped object against a current build: recover function boundaries from the unwind tables still present in the stripped binary, then match each function's bytes to the current build's functions with branch and page-relative immediates masked. Before that, read the backtrace's **shape** — an alternation between exactly two addresses is a two-node mutual recursion, the frame count is the unwinder's cap and not the depth, and the argument registers frequently still hold the failure's message text in ASCII. | `port-shipping` |
| On a slower device the controls stop responding entirely, and the guest keeps running while the app is in the background | Not a crash and not a leak: the event pump never yields, so everything the host does outside its tick — the input drain, the background-pause check, the frame pacing — is unreachable. See the timer-callback row in [§2.3](#23-rendering-frame-pacing-and-game-speed). | `emulator-core` |
| The app is frozen on a network screen after being backgrounded and resumed, with no network fault and no reproduction on a LAN | The OS destroyed the sockets of a cached process — see `ECONNABORTED` in [§1](#1-verbatim-messages). The frozen screen will not clear itself, so the repair has two halves: notice the dead socket, and raise the client's own screen-exit modal. | `server-revival` / `android-host` |

### 2.18 Tests and gates that pass wrongly

A green suite is a claim about something. These rows are about finding out *what* it is a claim
about. See [selftest-convention.md](selftest-convention.md) for the harness itself.

| symptom | what it actually means | skill |
|---|---|---|
| You delete a function from the application crate and its tests still pass | The test file is a hand-written **mirror** that re-declares the constants and functions, not an `include!` of the real source. It will stay green forever. Convert it; where the real module has a dependency you cannot yet hoist out, pin the mirror to the source **text** — read the real file at test time, slice out the function body, whitespace-normalise it and assert it still reads as the mirror claims, with a failure message naming what to update. | `port-shipping` |
| A green suite is defending the bug you just found, and the user is right | The assertion states the **current output** rather than the rule, so the test pins the bug — and this survives `include!`ing the shipping source, because `include!` prevents drift while freezing a wrong premise. A mis-named case comment is what makes it invisible to a reviewer. Grep the suite for the reported input *before* reading any code, re-derive every refusal list from the guest's own gate with the derivation cited in the assertion, prefer asserting the **shape** of that gate (upper bound only, no lower bound) over enumerating values, and add a positive test that the effect is actually emitted rather than merely permitted. | `port-shipping` |
| A whole group of controls or behaviours has no coverage even though a selftest file for that module exists and passes | The file is a drifted hand-written mirror whose enum or list predates those controls, so their cases are not merely untested — they are **unrepresentable** in the test. Convert it to `include!`; until then, itemise in the project's instructions exactly which parts the mirror does not cover, and do not count its assertions in the project's test tally. Expect mirrors to be partially updated: each session patches only what it touched. | `port-shipping` |
| A geometry suite is fully green while taps land on the wrong row or cell | Every test derives its expectations **from the constants under test**, so a mis-typed re-measurement satisfies all of them — even in a suite that `include!`s the real shipping source. Add one test that restates the raw measurements as literals, then validate the pin by mutating a constant and confirming that test, and ideally only that test plus one other, goes red. | `android-host` |
| A selftest passes locally and fails in CI with a file-not-found on a relative source path | The test reads project files (a mirror pinned to source text, a generated table) and depends on the working directory being the repository root. Make the runner change to the repository root, and have the assertion message say so verbatim. | `port-shipping` |
| The documented total test count does not match the sum of the documented per-file counts, or a selftest file exists that is not in the project's list | The list of test files is hand-maintained in a document, so the document **is** the registry and it drifts. A file missing from the list is a file nobody runs, and its absence produces no red. Ship one runner script that globs the test files, reads each one's required edition, runs from the repository root, prints a per-file pass count and the total, and exits non-zero on any failure. A count is an invariant only if a command prints it. | `port-shipping` |
| A quality gate (linter, formatter, conformance script) is recorded as passing, and the tool turns out not to be installed on that machine | The record was carried over from a different environment: a gate that exists only as a documented instruction gets reported rather than run. Put every gate in one script with an exit code and make it fail loudly, not skip silently, when a required tool is absent. Run a formatter only inside the vendored workspace — at the repository root it reformats crates that were never formatter-clean and destroys the reviewability of your diff against the fork. | `port-shipping` |
| An overlay or drawing module cannot be verified because no standalone test can include it | Overlay code legitimately references half the application crate, so the dependency-free selftest pattern does not apply. Two honest options: an ignored in-crate test that writes an image file for side-by-side comparison against a device screenshot, or a throwaway mirror renderer for shape judgement only, labelled "no correctness claim rests on this" and excluded from the test tally. Do the visual pass; a mock-up catches defects no assertion can. | `android-host` |
| Deleting superseded functions from a dependency-free module silently removes unrelated code | The module has no internal boundaries, so a line-range edit takes out whatever happens to sit between the targets. Treat compilation of the standalone selftest as the regression gate: run it immediately before and after any range edit of an included module, and read an unresolved-name error as the alarm. | `android-host` |
| The host test build stops compiling on a machine that previously ran the crate's own tests, some sessions after a JNI feature was added | A new module pulls a target-only crate with no target-OS gate, so the host-triple build cannot resolve it. Gate every module that touches a target-only dependency; the device build is unaffected. | `port-shipping` |

### 2.19 Build, sign, install and hand out

| symptom | what it actually means | skill |
|---|---|---|
| The build succeeds and the APK points at localhost, with online features dead for everyone but you | A build-time-baked constant resolved to nothing. `option_env!` is evaluated at compile time and a missing variable produces a *silent wrong build*, not an error. Three defences: resolve from persistent configuration rather than only the shell; hard-error on a release build with no destination; and scan the produced shared object for the expected string. The last one is the only check that cannot be fooled — note that the fallback string is always present, so "does it mention localhost" proves nothing; only presence of the **wanted** value does. | `port-shipping` |
| A rebuild "did nothing" and the old configuration is still baked in | A stale cargo fingerprint. This is exactly what the artifact scan catches; without it, the build is perfectly successful and wrong. | `port-shipping` |
| The debug APK is hundreds of megabytes | The strip stage was skipped. Strip in the build script for both profiles and tell the packaging step not to strip again. | `port-shipping` |
| Launching by an explicit component name fails with "class not found" | The application id and the Java package are deliberately different. Derive the launchable component from the built package's own metadata instead of composing it by hand. | `port-shipping` |
| PowerShell aborts a build step that actually succeeded | A stop-on-error preference combined with redirecting a native command's stderr. Many tools write ordinary progress to stderr. Do not redirect; check the exit code explicitly. | `port-shipping` |
| A properties file's comments are corrupted, or the build reads the wrong version | The file was rewritten with a BOM or through the console code page, and the consuming loader decodes it as Latin-1. Write it with an explicit no-BOM UTF-8 writer and keep the file ASCII-only. | `port-shipping` |
| `cargo test -p <app-crate>` dies immediately | The application crate's platform link graph. Expected. Use the standalone selftest harness — see [selftest-convention.md](selftest-convention.md). | `port-shipping` |
| A bare `cargo build --target aarch64-linux-android` links against a different API level than the app declares | A stale linker configuration file with absolute paths and its own API level. The wrapper tool's environment variables win when you go through it, so the file is dead config *until* somebody bypasses the wrapper. Delete it. | `port-shipping` |
| The fork cannot be diffed against upstream or rebased | The vendored core was copied rather than tracked, and no base commit was recorded. Record repository URL, base commit and date in a file next to the vendored tree, refreshed on every re-vendor. | `emulator-core` / `port-shipping` |
| Inherited CI fails on a workspace-wide test run | The inherited workflow tries to host-build the application crate. Replace it with a job that runs the selftests, the vendored core's own tests, and a cross-compile build. | `port-shipping` |
| A reported bug is fixed in your code, the logs from the device look correct, and the report keeps arriving unchanged | The reporter is running a different build from the one you verified. With more than one test device, only the connected one appears in the device list, so a build installed on the device on your desk gets recorded as "verified on device" while the reporter plays an older build on the other one. Read the installed version off the **reporting** device before reading anything else, address every device command to an explicit serial, and keep a per-device row naming which build is on it — with the query command next to it, and a note that the row goes stale. | `port-shipping` |
| A recalled or intermediate build is handed to someone weeks after it was superseded | The distribution directory held more than one artifact, and the recall was recorded only in the release notes of the version that fixed it — not in the document the next distributor reads first. Keep exactly one build in the distribution directory, write the recall as a line naming the affected version ceiling and the mechanism in the first-read project document as well as the handout, and separate RECALLED (can destroy player data) from DO NOT HAND OUT (a mid-session intermediate). A withdrawn build is not recallable: the only remedies are a higher version code and a written statement of the range. | `port-shipping` |
| Comparing two behaviours on a device requires installing the previous build, which the installer refuses as a downgrade | And a downgrade requires an uninstall, which deletes the save you were comparing against. Put every behavioural switch behind a file searched first in the app-specific external directory (a shell can write there on a release build), read once at startup, with a log line naming the winning path. The comparison then becomes the same phone, the same save, one restart apart. The same hatch serves a one-shot command file for data you cannot edit through the UI — read it at launch, apply it, then delete it so it cannot run twice, and scope it to your own store, never to save records. | `port-shipping` / `android-host` |
| You cannot determine which configuration a shipping build actually resolved, and the developer's own device works | App-private storage is unreachable over the debug bridge on a non-debuggable package, so a stale on-device override can silently shadow the value baked into the artifact with nothing anywhere to say so — and the artifact-verification gate is satisfied while the app misbehaves. Make the app report its effective configuration and, for each value, where it came from and what it overrode. Put the operator's values in the boot log rather than on the player-facing screen. | `port-shipping` |
| A performance comparison is not reproducible, or shows the interpreter consuming far more CPU than the code justifies | Three candidates. You measured a **debuggable** artifact — setting the optimisation level on the debug profile does not disable debug assertions or overflow checks, and an interpreter pays an overflow check on every arithmetic operation (the same scene moved one thread from 89.6 % to 64.5 % of a core when switched). A vendor power or game-management policy has capped the big cores at the little cores' maximum frequency, which cannot be lifted from application code. Or the host produced outliers: interleave runs and take the median. Read the package's own flags, compare each CPU policy's administrative maximum against its hardware maximum, and record which build and clock state produced each figure. | `port-shipping` |

### 2.20 Publish and secrets

| symptom | what it actually means | skill |
|---|---|---|
| A secret is gone from the working tree but still in the repository | Ignore rules prevent future additions and never remove past ones. Audit **all refs**, not the working tree — and remember that a history purge is undone by the backup branch you made "just in case". | `port-shipping` |
| Licensed content leaks despite an ignore rule for its directory | A tool wrote a byte-identical copy under a different name in a different directory, and the rule only guarded one path. Guard by **name** as well as by path. | `port-shipping` / `archive-prep` |
| A distributed build embeds content you did not intend to publish | A packaged application contains the game archive *and* the baked configuration. A source-tree purge cannot succeed while built artifacts are tracked. | `port-shipping` |
| Real user data ends up in the source tree | Default state and log paths point at the package directory. Default them outside the source tree, or require the path to be given explicitly. | `server-revival` |

| A public repository built from this methodology contains the game's font bitmaps or icon art | The extracted tables were committed as generated **source** (a `.rs`/`.c` file) or embedded as a blob inside the application crate, where ignore rules and reviewers keyed on archive extensions, a working directory or the word "atlas" do not see them. Publish the generator and the format notes, generate the table at build time from the user's own archive, and ignore generated tables by **content origin** rather than by extension or directory. | `port-shipping` / `archive-prep` |

## 3. Faults that look like a different phase's fault

The most expensive failures in this methodology are the ones whose symptom points at the wrong
layer. Keep this short list in mind when a fix is not working.

| looks like | actually is |
|---|---|
| A black screen "in the game" | Almost never the game. In order of likelihood: no virtual clock (headless), a fatal unimplemented stub, an archive fault that panicked on the async boot task, or a missing bundled asset. |
| A black screen a second or two **after** the title screen, with an allocation failure or a fatal error far from anything you changed | A stale **generated asset**: a data member and a guest constant disagree about a row count, so the parser walks off the array and computes a negative length. Nothing upstream of the phone can see it — the build script, the signature verification and a launch-and-look smoke test all pass, because the death is after the title. See [§2.2](#22-generated-and-patched-assets). |
| A crash | If there is no tombstone, it is not a crash. An OS memory kill and a hang both reach the player as "the app closed and came back at the title". Read the process-exit history before concluding anything about whether a crash fix landed. See [§2.16](#217-process-death-crashes-os-kills-and-hangs). |
| A protocol bug | Frequently a host socket-layer bug: a stubbed read callback, a wrong no-data sentinel, an unclamped `recv`, or an error status reported as not-readable. Rule those out before touching the frame format. |
| A protocol bug during a purchase, transfer or delivery | Frequently a **client-fidelity** bug: your quantity model is not the client's placement procedure, and the divergence only shows on nearly-full inventories. See [§2.14](#214-network-and-replacement-server). |
| A game-logic bug in your host reimplementation | Frequently a stale pointer that was never validated, a struct offset with only one derivation, or a **derived cache** you did not rebuild — the value the screen shows is not always the value you wrote. |
| A rule of the game ("this item type just is not supported") | Frequently your own silent pre-filter, or a bound your host reimplementation narrowed while the game's own gate was upper-bound-only. It reaches you as a question about game design, not as a bug report — which is why it survives so long. |
| Save-file corruption | Never corruption: a deletion or a truncation. The guest's slot list can only report "empty" for a missing, zero-length or checksum-failed record, and its summary builder cannot express failure. See [§2.8](#28-save-data-loss-slots-and-restore). |
| An emulator opcode bug | Almost never. Expect not to need opcode work on a commercial ARM feature-phone binary; spend the budget on the platform API surface instead. A *silently* wrong opcode presents as garbage state and a fault at an unrelated address, so if you must chase one, use instruction tracing or the debug server rather than reasoning. |
| An audio bug | Frequently not the audio code at all. A hitch on every sound is usually the archive resource path or a synchronous platform call on the emulator thread; music that **starts over from the beginning** is the guest's single sound slot, not your mixer; and effects that vanish only when the player turns everything up are a limiter on the sum, not a level. |
| A touch or input bug confined to one family of screens | Frequently an application-state word that means two unrelated things, so a gate written for one meaning silently refuses the other. Grep for every use of that constant, not just the one you are looking at. |
| A game-speed complaint | Frequently your own clamp on the guest's frame-timer period: on this class of title that period *is* the speed option, and a ceiling clamp rewrites every slower setting. |
| A device that is simply too slow | Check that you measured a release artifact, and compare each CPU policy's administrative maximum against its hardware maximum. An administratively throttled phone looks architecturally slow. |
| A firewall problem | Frequently a compile-time destination constant. Prove the client is aiming at a public address first. |
| A test that is passing | Two ways it can be worthless, and the second is invisible to the usual fix. Is it a hand-kept **mirror** of the shipping source rather than an `include!` of it? Then it is passing about a copy. Or does the assertion state the current **output** rather than the rule? Then it is passing about the bug — and that one survives `include!`ing the shipping source, because `include!` prevents drift while freezing a wrong premise. Grep the suite for the reported input before you read any code. |
